# 計算の確かめ方（網羅の計画）

Create の計算（回転・応力・物の通り道・輸送量・回転と反転・置き方）が、扱うブロックすべてについて正しいかを確かめる計画。「網羅した」と言える範囲をはっきり決め、抜けをテストで見つけられるようにする。

規則そのものは [create-stress.md](create-stress.md) と [create-throughput.md](create-throughput.md) に書く。この書類は、それをどう確かめ、どこまで確かめたかを扱う。

## 「網羅した」の意味

手で並べた一覧は、並べ忘れに気づけない。そこで、確かめる対象を **外から決まる閉じた一覧** にして、その一覧の項目に抜けがないかをテストで調べる。一覧は次の5つ。

| 一覧 | 何の全部か | どこから取るか | 抜けの調べ方 |
| --- | --- | --- | --- |
| 1. ブロック | 対象の版の Create のすべてのブロック | 利用者の jar の `assets/create/blockstates/` のファイル名 | すべての ID に、機能ごとの分類があること |
| 2. 状態 | 計算が読むプロパティと生データの項目の、とりうる値の全部 | jar の blockstates の `variants`・`multipart`、Create のソース | 計算が読む項目の値の組み合わせを、テストが全部通ること |
| 3. 規則 | 書類に書いた規則の全部 | 書類（規則に ID を付ける） | すべての規則 ID に、出典とテストがあること |
| 4. 分岐 | 計算のコードのすべての分岐 | `src/calc/create/` | 分岐の網羅率。通らない分岐は理由付きで一覧にする |
| 5. 数値 | 計算に使う定数の全部 | `src/calc/create/` の定数 | すべての定数に、出典の規則 ID があること |

5つの一覧はつながっている。ブロック（1）は状態（2）を持ち、状態ごとに規則（3）が決まる。規則はコード（4）と数値（5）で実装される。どの向きにたどっても行き止まりがないことを調べる。

- ブロック → 規則：計算で扱うブロックには、規則がある。扱わないブロックには、扱わない理由がある。
- 規則 → テスト：規則には、それを確かめるテストがある。
- コード → 規則：分岐と定数には、それが実装する規則がある。書類にない動きはコードに置かない。

### 保証できること・できないこと

保証できること：

- 対象の版の Create の、すべてのブロックについて、機能ごとに「扱う」か「扱わない（理由）」かが決まっている。
- 扱う規則はすべて、出典（Create のソースのファイルと式）とテストを持つ。
- 計算のコードのすべての分岐と定数が、書類の規則に対応している。
- それぞれの規則を、下の A〜D のどの段階まで確かめたかが分かる。

保証できないこと：

- ゲームの動きそのもの。ソースを読み違えていればテストも同じように間違う。ゲームで測った（段階 D）規則だけが、ゲームと合っていると言える。
- 対象の版以外の Create、Create のアドオン、ほかの Mod のブロック（入れ物として扱う一般の規則だけを確かめる）。
- KubeJS などで変えたレシピの中身（レシピの読み方は確かめるが、Modpack ごとの値は確かめない）。

## 1. ブロックの一覧

### 一覧の作り方

Create はブロックの名前の一部をコードで組み立てる（色違い・木の種類違いなど）。そのため、ソースの `AllBlocks.java` を読むだけでは全部が取れない。全部のブロックは、jar の `assets/create/blockstates/` に1つずつファイルがある。そこで、利用者の jar からファイル名だけを取り出して、版ごとの ID の一覧にする。

- 取り出すのは ID（ファイル名）だけ。中身（モデル・テクスチャ・翻訳）は取らない。
- 一覧を作るスクリプトは、jar の場所を引数にとる。jar はリポジトリに入れない。

### 分類

ID ごとに、機能ごとの分類を持つ。

| 機能 | 値 |
| --- | --- |
| 回転のつながり | 扱う（形）／回転しない |
| 応力 | 消費・供給の値がある／ない |
| 物の通り道 | 扱う（規則 ID）／入れ物として扱う／通さない／扱わない（理由） |
| 輸送量・処理時間 | 扱う（規則 ID）／ない |
| 回転・反転 | 扱う（使うプロパティ）／向きを持たない |
| 置き方・初期状態 | 扱う／ない |

「扱わない」には理由を書く（「#235 で足す」「物を運ばない」など）。理由のない「扱わない」は許さない。

Minecraft 本体のブロックは数が多いので、ID ごとには分類しない。計算が名前で扱うもの（ホッパー・チェストなど）だけを一覧に載せ、残りは「入れ物（ブロックエンティティがある）」「当たり判定がある」「空気」の一般の規則で扱う。

### 調べること（テスト）

- 一覧のすべての ID に、すべての機能の分類がある。
- コードが名前で扱う ID（`'create:belt'`、`path === 'gearbox'` など）が、どれかの版の一覧にある。綴りの誤りや、版にないブロックを見つける。
- 分類が「扱う」の ID は、その機能のテストに出てくる。

## 2. 状態の組み合わせ

扱うブロックごとに、計算が読むプロパティと生データの項目を並べる。値の範囲は jar の blockstates（プロパティ）と Create のソース（生データ）から取る。

| 例 | 読む項目 | 値の範囲 |
| --- | --- | --- |
| ベルト | `facing`・`slope`・`part`・`casing` | 4 × 5 × 4 × 2 |
| ベルトのファンネル | `facing`・`shape`・`powered` | 4 × 4 × 2 |
| 重さ付きイジェクター | `facing`、生データの `HorizontalDistance`・`VerticalDistance` | 4、距離は 0〜（設定の上限） |
| 真鍮のトンネル | 生データの `ScrollValue`、隣のトンネル | 7 つの分け方 |

- テストは表で全組み合わせを回す。回転数の符号（正・負・0）も組み合わせに入れる。
- 期待値は、コードの式をなぞらずに、規則から独立に書く（向きの表など）。
- 組み合わせが多すぎるときは、互いに関係しない項目に分け、それぞれを全部回す。分けた理由を書く。

## 3. 規則の一覧

- [create-stress.md](create-stress.md)・[create-throughput.md](create-throughput.md) の規則に ID を付ける（例：`TP-BELT-DIR`、ベルトの進む向き）。表の行や箇条書きの1つが、1つの規則。
- 規則ごとに、出典（Create のソースのファイルと式。版で違えば両方）と、確かめた段階（下の A〜D）を書く。
- テストの名前に規則 ID を入れる（`it('[TP-BELT-DIR] …')`）。
- 調べること：書類のすべての規則 ID がテストに出てくる。テストに出てくる ID がすべて書類にある。

## 4. コードの分岐

- `src/calc/create/` の分岐の網羅率を測る（Vitest の coverage。`@vitest/coverage-v8` を足す）。
- 目標は分岐 100%。通らない分岐は、規則が書類にない（書類に足してテストを書く）か、要らない（消す）かのどちらか。
- どうしても通せない分岐（守りのための分岐など）は、理由付きで一覧にする。一覧にないのに通らない分岐があれば、テストを失敗させる。

## 5. 数値

- 計算に使う定数（`HOPPER_TICKS = 8` など）をすべて一覧にし、規則 ID と出典を付ける。
- README の「注記」に、出典とライセンスが書かれていることを確かめる。

## 確かめる段階

規則ごとに、どこまで確かめたかを記録する。

| 段階 | すること | 誰が |
| --- | --- | --- |
| A. ソースとの照合 | 規則と数値を、Create のソースの式・定数と見比べる。両方の版で見る | 開発 |
| B. 固定のテスト | 規則ごとに、コードで小さな設計図を作り、期待値をテストに書く（上の 2・3） | 開発 |
| C. 実在の設計図 | 公開されている設計図を手元で計算に通し、おかしな流れ・多すぎる仮定がないかを見る。設計図はリポジトリに入れない | 開発 |
| D. ゲームで測る | 試験台の設計図をゲームに置き、数・時間・行き先を測って、アプリの値と比べる | 利用者 |

### ゲームで測る（D）

- 試験台は、どれも同じ形にする。クリエイティブモーターで回転数を決め、クリエイティブクレートからファンネルで物を入れ、調べるブロックを通して、チェストで受ける。
- 回転数を変えた版（16・64・256 RPM）を作る。向きの規則は、回転数の符号を変えた版も作る。
- 試験台はコードで作る（`tests/fixtures/`）。作った .nbt は作業用のフォルダに書き出し、リポジトリに入れない。
- 試験台ごとに、手順（何秒測るか、何を数えるか）と、アプリが出す期待値を書いた表を付ける。
- 測った値は、規則ごとに記録する。合わなければ、規則とコードを直す。
- ゲームでしか分からないこと（同じ区間のベルトのファンネルとデプロイヤーのどちらが先か、機械アームの配り方など）は、先に D を行う。

### 実在の設計図で確かめる（C）

`tests/verification/realBlueprints.test.ts`。環境変数を渡したときだけ動く（ふだんの `npm run test` では飛ばす）。設計図と Modpack は利用者の PC にあるものを読むだけで、リポジトリには入れない。KubeJS のスクリプトは動かさない。

```
MINECIRCUIT_BLUEPRINTS="<設計図のフォルダ>" MINECIRCUIT_MODPACK="<Modpack のフォルダ>" MINECIRCUIT_REPORT="<報告の .md>" npx vitest run tests/verification/realBlueprints.test.ts
```

- `MINECIRCUIT_BLUEPRINTS` は `;` で区切って複数のフォルダを渡せる。中のフォルダも探す。`MINECIRCUIT_MODPACK` と `MINECIRCUIT_REPORT` は省ける。報告はリポジトリの外に書く。
- テストを失敗させること：読めない、計算が止まる、その版のブロックの一覧にない Create の ID がある、回転数が数でない、回転・つながりが設計図の外にある、物の流れの数や時間がおかしい。
- 報告に書くこと：まとめ、問題と仮定の種類ごとの数、問題の場所、ゲームが生データに保存した回転数（`Speed`）と計算の回転数の比較。比較は、設計図の外から回されていたブロックや、保存のあとで変えた設計図では違ってよいので、失敗にはしない。違うブロックは1つずつ理由を見る。

## 記録

- 分類（1）と、規則ごとの段階（3）は、コードのデータに持つ。テストがそれを読んで抜けを調べる。
- 書類の状態の表は、そのデータから作る。手で二重に書かない。

## 進め方

| 順 | 内容 |
| --- | --- |
| 1 | 仕組み：ブロックの一覧を jar から作るスクリプト（ID の一覧はリポジトリに入れる）、分類のデータ、規則 ID、分岐の網羅率、抜けを調べるテスト。この時点の抜けを一覧にする |

### 調べていること

- コードが名前で扱う Create のブロック・ブロックエンティティの種類が、どれかの版にあること。
- Create で回るブロック（`KineticBlockEntity` を継ぐクラスのブロック）と、計算で回るブロックが一致すること。
- すべてのブロックで、応力の初期値が Create のソースと一致すること。
- すべてのブロックエンティティの種類に、物の通り道での扱いが決まっていること。たどる種類にはコードに処理があり、たどらない種類にはないこと。
- すべてのブロックの、プロパティの値のすべての組み合わせ（多すぎるブロックは1つずつ）で、4回まわすと元に戻ること、反転2回で元に戻ること、値が範囲を出ないこと、東西南北の値が 90° で変わること。
- 応力（`ST-…`）・物の通り道と輸送量（`TP-…`）・回転と反転（`TF-…`）・置き方と初期状態（`PL-…`）の規則がすべてテストの名前に出てくること。テストに出てくる ID が書類にあること。
- 回転軸の表の行ごとに、向き・軸の値から決まる回転軸・軸の口・歯車が表のとおりであること。

### まだ仕組みがないもの

- 数値の一覧（5）。
- 実在の設計図（C）の量。手元に Create の回る仕掛けの設計図が1つしかない。公開されている設計図（Create の歯車・ベルト・機械を使ったもの）を利用者が手元に集めれば、同じ手順で通せる。物の流れは、物の入口（仮の入出力）を置かないと通らないので、別に考える。
- 通せない分岐の一覧（4）。kineticGraph.ts に残る分岐は、複数のリージョンが重なる設計図、ゲームが残さない状態（横を向いていないベルトなど）、ノードの並び順で通らない向きの判定。createItemPath.ts に残る分岐の多くは、値がないときの初期値（`?? 0` など）と、ゲームが残さない状態（向きのない取り出すファンネルなど）。createTransform.ts に残る分岐は、ゲームが残さない状態（true・false でない値、`window_` で始まるのに4つの向きにない窓、x・z でない `horizontal_axis`、`axis` のないチェーンドライブ）と、呼ぶ前に除いている値（6方向のどれかにならない向き、読めない位置の書き戻し）。createBasicBlocks.ts の1つは、どの部品も補えるので通らない。
- 状態の組み合わせ（2）のうち、回転のつながり・物の通り道を、すべての組み合わせで回すテスト。今は回転・反転だけ。

## 決めたこと

- **ブロックの ID の一覧はリポジトリに入れる。** 名前だけで、モデル・テクスチャ・翻訳は入れない。CI で抜けを調べられるようにするため。一覧には、取り出した jar のファイル名と版を書く。
- **`@vitest/coverage-v8` を開発用の依存に足す。** 分岐の網羅率を測るため。アプリには入らない。
