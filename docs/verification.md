# 計算の確かめ方（網羅の計画）

計算プラグインの計算が、扱うブロックすべてについて正しいかを確かめる決まり。どの Mod の計算にも同じ決まりを使う。「網羅した」と言える範囲をはっきり決め、抜けをテストで見つけられるようにする。

規則そのものは、Mod ごとの書類に書く。この書類は、それをどう確かめ、どこまで確かめたかの決まりを扱う。Mod ごとの一覧の置き場所・対象の版・今の状態は、その Mod の確かめ方の書類に書く。

| 計算プラグイン | 規則の書類 | 確かめ方の書類 |
| --- | --- | --- |
| Create（回転・応力・物の通り道・輸送量・回転と反転・置き方） | [create-stress.md](create-stress.md)・[create-throughput.md](create-throughput.md) | [create-verification.md](create-verification.md) |

計算プラグインを足すときは、この表に行を足し、同じ形の確かめ方の書類を作る。

## 「網羅した」の意味

手で並べた一覧は、並べ忘れに気づけない。そこで、確かめる対象を **外から決まる閉じた一覧** にして、その一覧の項目に抜けがないかをテストで調べる。一覧は次の5つ。

| 一覧 | 何の全部か | どこから取るか | 抜けの調べ方 |
| --- | --- | --- | --- |
| 1. ブロック | 対象の版の Mod のすべてのブロック | 利用者の jar の `assets/<namespace>/blockstates/` のファイル名 | すべての ID に、機能ごとの分類があること |
| 2. 状態 | 計算が読むプロパティと生データの項目の、とりうる値の全部 | jar の blockstates の `variants`・`multipart`、Mod のソース | 計算が読む項目の値の組み合わせを、テストが全部通ること |
| 3. 規則 | 書類に書いた規則の全部 | 書類（規則に ID を付ける） | すべての規則 ID に、出典とテストがあること |
| 4. 分岐 | 計算のコードのすべての分岐 | そのプラグインのフォルダ（`src/calc/<Mod>/`） | 分岐の網羅率。通らない分岐は理由付きで一覧にする |
| 5. 数値 | 計算に使う定数の全部 | そのプラグインのフォルダの定数 | すべての定数に、出典の規則 ID があること |

5つの一覧はつながっている。ブロック（1）は状態（2）を持ち、状態ごとに規則（3）が決まる。規則はコード（4）と数値（5）で実装される。どの向きにたどっても行き止まりがないことを調べる。

- ブロック → 規則：計算で扱うブロックには、規則がある。扱わないブロックには、扱わない理由がある。
- 規則 → テスト：規則には、それを確かめるテストがある。
- コード → 規則：分岐と定数には、それが実装する規則がある。書類にない動きはコードに置かない。

### 保証できること・できないこと

保証できること：

- 対象の版の Mod の、すべてのブロックについて、機能ごとに「扱う」か「扱わない（理由）」かが決まっている。
- 扱う規則はすべて、出典（Mod のソースのファイルと式）とテストを持つ。
- 計算のコードのすべての分岐と定数が、書類の規則に対応している。
- それぞれの規則を、下の A〜D のどの段階まで確かめたかが分かる。

保証できないこと：

- ゲームの動きそのもの。ソースを読み違えていればテストも同じように間違う。ゲームで測った（段階 D）規則だけが、ゲームと合っていると言える。
- 対象の版以外の Mod、その Mod のアドオン、ほかの Mod のブロック（入れ物として扱う一般の規則だけを確かめる）。
- KubeJS などで変えたレシピの中身（レシピの読み方は確かめるが、Modpack ごとの値は確かめない）。

## 1. ブロックの一覧

### 一覧の作り方

Mod はブロックの名前の一部をコードで組み立てることがある（色違い・木の種類違いなど）。そのため、ソースを読むだけでは全部が取れない。全部のブロックは、jar の `assets/<namespace>/blockstates/` に1つずつファイルがある。そこで、利用者の jar からファイル名だけを取り出して、版ごとの ID の一覧にする（`scripts/extractBlockIds.mjs`）。

- 取り出すのは ID（ファイル名）と、プロパティの値の範囲だけ。中身（モデル・テクスチャ・翻訳）は取らない。
- 一覧を作るスクリプトは、jar の場所を引数にとる。jar はリポジトリに入れない。

### 分類

ID ごとに、機能ごとの分類を持つ。機能はプラグインが計算するものから決める（Create なら回転のつながり・応力・物の通り道など）。値は「扱う（形・規則 ID など）」か「扱わない（理由）」。

「扱わない」には理由を書く（「#235 で足す」「物を運ばない」など）。理由のない「扱わない」は許さない。

Minecraft 本体のブロックは数が多いので、ID ごとには分類しない。計算が名前で扱うもの（ホッパー・チェストなど）だけを一覧に載せ、残りは「入れ物（ブロックエンティティがある）」「当たり判定がある」「空気」の一般の規則で扱う。

### 調べること（テスト）

- 一覧のすべての ID に、すべての機能の分類がある。
- コードが名前で扱う ID が、どれかの版の一覧にある。綴りの誤りや、版にないブロックを見つける。
- 分類が「扱う」の ID は、その機能のテストに出てくる。

## 2. 状態の組み合わせ

扱うブロックごとに、計算が読むプロパティと生データの項目を並べる。値の範囲は jar の blockstates（プロパティ）と Mod のソース（生データ）から取る。

- テストは表で全組み合わせを回す。計算の入力の符号（回転数の正・負・0 など）も組み合わせに入れる。
- 期待値は、コードの式をなぞらずに、規則から独立に書く（向きの表など）。
- 組み合わせが多すぎるときは、互いに関係しない項目に分け、それぞれを全部回す。分けた理由を書く。

## 3. 規則の一覧

- 規則の書類の規則に ID を付ける（例：`TP-BELT-DIR`、Create のベルトの進む向き）。表の行や箇条書きの1つが、1つの規則。ID の頭の文字は書類ごとに決める。
- 規則ごとに、出典（Mod のソースのファイルと式。版で違えば両方）と、確かめた段階（下の A〜D）を書く。
- テストの名前に規則 ID を入れる（`it('[TP-BELT-DIR] …')`）。
- 調べること：書類のすべての規則 ID がテストに出てくる。テストに出てくる ID がすべて書類にある。

## 4. コードの分岐

- プラグインのフォルダの分岐の網羅率を測る（Vitest の coverage。`vitest.config.ts`、`npm run coverage`）。
- 目標は分岐 100%。通らない分岐は、規則が書類にない（書類に足してテストを書く）か、要らない（消す）かのどちらか。
- どうしても通せない分岐（守りのための分岐など）は、理由付きで一覧にする。一覧にないのに通らない分岐があれば、テストを失敗させる。

## 5. 数値

- 計算に使う定数をすべて一覧にし、規則 ID と出典を付ける。
- README の「注記」に、出典とライセンスが書かれていることを確かめる。

### 一覧の作り方

名前の付いた定数だけを並べると、関数の中に直に書いた数（`Math.abs(rpm) / 24` の 24 など）が抜ける。そこで、プラグインのフォルダのテスト以外のファイルにある **数の字句すべて** を対象にする。

- 数は、それを含む宣言（一番外の定数・関数・クラスのメソッド）ごとにまとめる。一覧の見出しは `ファイル名#宣言の名前`（例：`createThroughput.ts#beltSpeed`）。行の番号は使わない（行がずれるたびに直すことになるため）。
- 0 と 1、配列の添字（`pos[2]` の 2）は数えない。どれも規則の値ではないため。

| 種類 | 何か | 要るもの |
| --- | --- | --- |
| `game` | Mod・Minecraft のソースから読んだ値（初期値・式の係数・時間） | 規則 ID（1つ以上）。そのファイルが README の「注記」に出典とライセンス付きで載っていること |
| `app` | このアプリが決めた値（見た目、たどる数の上限、誤差の許し、仮の入出力の初期値など） | 理由。規則があれば規則 ID |
| `math` | 規則によらない値（1分 = 60 秒、百分率の 100、ブロックの真ん中の 0.5、座標が3つ、文字列の長さなど） | 理由 |

### 調べること（テスト）

TypeScript の構文木を読んで次を調べる。

- コードのどの宣言の数も、一覧の同じ見出しの数と、重なりも含めて一致する。数を足す・変えると失敗するので、一覧も直すことになる。
- 一覧の見出しは、どれもコードにある（消した宣言が残らない）。
- `game` の規則 ID はどれも規則の一覧にある。`app`・`math` には理由がある。
- `game` の数があるファイルは、どれも README の「注記」に名前が出てくる。

## 確かめる段階

規則ごとに、どこまで確かめたかを記録する。

| 段階 | すること | 誰が |
| --- | --- | --- |
| A. ソースとの照合 | 規則と数値を、Mod のソースの式・定数と見比べる。対象のすべての版で見る | 開発 |
| B. 固定のテスト | 規則ごとに、コードで小さな設計図を作り、期待値をテストに書く（上の 2・3） | 開発 |
| C. 実在の設計図 | 公開されている設計図を手元で計算に通し、おかしな値・多すぎる仮定がないかを見る。設計図はリポジトリに入れない | 開発 |
| D. ゲームで測る | 試験台の設計図をゲームに置き、値・時間・行き先を測って、アプリの値と比べる | 利用者 |

### ゲームで測る（D）

- 試験台はコードで作る（`tests/fixtures/<Mod>/`）。どれも、対象の版のブロックの一覧にあるプロパティをすべて書き、計算が考えたとおりに動き、ゲームで外れる置き方がないことをテストで確かめる。
- 作った .nbt は作業用のフォルダに書き出し、リポジトリに入れない。書き出すと、試験台ごとの手順と、アプリが出す期待値の表（「手順.md」）も作る。Modpack を渡すと、期待値をその Modpack の設定とレシピで計算する。
- 測った値は、規則ごとに記録する。合わなければ、規則とコードを直す。
- ゲームでしか分からないことは、先に D を行う。

### 実在の設計図で確かめる（C）

- 環境変数を渡したときだけ動くテストにする（ふだんの `npm run test` では飛ばす）。設計図と Modpack は利用者の PC にあるものを読むだけで、リポジトリには入れない。KubeJS のスクリプトは動かさない。
- テストを失敗させるのは、読めない・計算が止まる・一覧にない ID がある・値が数でない・設計図の外の位置が出る、など明らかな誤り。ゲームが保存した値との比較は、保存のあとで変えた設計図などでは違ってよいので、失敗にはせず報告に書き、違うものは1つずつ理由を見る。

## 記録

- 分類（1）と、規則ごとの段階（3）は、コードのデータに持つ。テストがそれを読んで抜けを調べる。
- 書類の状態の表は、そのデータから作る。手で二重に書かない。

## 決めたこと

- **ブロックの ID の一覧はリポジトリに入れる。** 名前とプロパティの値の範囲だけで、モデル・テクスチャ・翻訳は入れない。CI で抜けを調べられるようにするため。一覧には、取り出した jar のファイル名と版を書く。
- **`@vitest/coverage-v8` を開発用の依存に足す。** 分岐の網羅率を測るため。アプリには入らない。
