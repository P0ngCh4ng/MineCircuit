# Create の計算の確かめ方

Create の計算（回転・応力・物の通り道・輸送量・回転と反転・置き方）が、扱うブロックすべてについて正しいかを確かめた記録。確かめ方の決まり（5つの一覧、確かめる段階 A〜D）は [verification.md](verification.md) に書く。この書類は、Create での一覧の置き場所・対象の版・試験台・今の状態を扱う。

規則そのものは [create-stress.md](create-stress.md) と [create-throughput.md](create-throughput.md) に書く。

## 対象の版

| 環境 | Create | 出典 |
| --- | --- | --- |
| Create Astral（Fabric 1.18.2） | 0.5.1 | `Fabricators-of-Create/create` の `80ecefb` |
| ATM10（NeoForge 1.21.1） | 6.0 | `Creators-of-Create/Create` の `7ff2760` |

[create-stress.md](create-stress.md)・[create-throughput.md](create-throughput.md) と同じ。版を足すときは、ブロックの一覧（1）から作り直す。

## 1. ブロックの一覧

Create の全部のブロックは、jar の `assets/create/blockstates/` に1つずつファイルがある（ソースの `AllBlocks.java` を読むだけでは、色違い・木の種類違いなどが取れない）。一覧は `tests/verification/blocks/` に版ごとに置く。

### 分類

| 機能 | 値 |
| --- | --- |
| 回転のつながり | 扱う（形）／回転しない |
| 応力 | 消費・供給の値がある／ない |
| 物の通り道 | 扱う（規則 ID）／入れ物として扱う／通さない／扱わない（理由） |
| 輸送量・処理時間 | 扱う（規則 ID）／ない |
| 回転・反転 | 扱う（使うプロパティ）／向きを持たない |
| 置き方・初期状態 | 扱う／ない |

「扱わない」には理由を書く（「#235 で足す」「物を運ばない」など）。理由のない「扱わない」は許さない。

### 調べること（テスト）

- 一覧のすべての ID に、すべての機能の分類がある。
- コードが名前で扱う ID（`'create:belt'`、`path === 'gearbox'` など）が、どれかの版の一覧にある。綴りの誤りや、版にないブロックを見つける。
- 分類が「扱う」の ID は、その機能のテストに出てくる。

## 2. 状態の組み合わせ

扱うブロックごとに、計算が読むプロパティと生データの項目を並べる。値の範囲は jar の blockstates（プロパティ）と Create のソース（生データ）から取る。

| 例 | 読む項目 | 値の範囲 |
| --- | --- | --- |
| ベルト | `facing`・`slope`・`part`・`casing` | 4 × 5 × 4 × 2 |
| ベルトのファンネル | `facing`・`shape`・`powered` | 4 × 4 × 2 |
| 重さ付きイジェクター | `facing`、生データの `HorizontalDistance`・`VerticalDistance` | 4、距離は 0〜（設定の上限） |
| 真鍮のトンネル | 生データの `ScrollValue`、隣のトンネル | 7 つの分け方 |

テストでは回転数の符号（正・負・0）も組み合わせに入れる。

組み合わせごとの期待値は、コードの式をなぞらずに、性質で書く。

- 回転・反転（`createTransform.test.ts`）：4回まわすと元に戻る、値の範囲を出ない、など。
- 回転の形（`createKineticStates.test.ts`）：回るブロックのすべての状態で、ブロックをまわす・反転すると、回転軸・軸の口・歯車・面の係数・チェーン・ガントリーの向きも同じだけ動く。回転数は「軸の正の向きから見て」なので、軸の正の向きが負の向きに移る軸の面は係数の符号が変わり、反転は回る向きを全部逆にする。
- 物の通り道（`createItemPathStates.test.ts`）：たどるブロックのすべての状態で、ブロックを真ん中に置いて6つの面にチェストを並べ、物の入口と（回るブロックなら）仮の動力源を付ける。設計図ごとまわす・反転すると、物のつながり（どこからどこへ）も同じだけ動く。仮の動力源の回転数は、まわしたあとも同じ向きに回るよう符号を合わせる。
- 物の通り道の置き方（`createItemPathLayouts.test.ts`）：上の置き方では物が流れないブロックを、物が流れる置き方に置き、そのブロックのすべての状態で確かめる。置き方ごとまわす（90°・180°）・反転する（x・z）と、物のつながりと物の動き（どこからどこへ・何を・何個/秒・移動の秒数・止まる秒数・道の形）も同じだけ動く。ベルトの上のものは、回転数の正と負（進む向きの両方）で通す。レシピはテスト用のもの（物が変わることだけを見る）を Modpack の代わりに渡す。

  | 置き方 | 状態をすべて変えるブロック |
  | --- | --- |
  | ベルトの上のベルトのファンネル（まわりにチェスト。後ろのチェストからも押し出す） | ベルトのファンネル（安山岩・真鍮） |
  | デポの上のベルトのファンネル（まわりにチェスト） | ベルトのファンネル（安山岩・真鍮） |
  | ベルトの上のトンネル（横にチェスト。真鍮は生データなしと `ScrollValue` 4） | トンネル（安山岩・真鍮） |
  | 並んだ2本のベルトの上の真鍮のトンネル（組の両端の横にチェスト） | 真鍮のトンネル |
  | ベルトの2段上のプレス・デプロイヤー・スパウト（スパウトは横に水） | プレス・デプロイヤー・スパウト |
  | デポの2段上のプレス（デポから取り出すファンネル） | プレス |
  | ベイスンの2段上のプレス・ミキサー（下のまわりにチェスト） | ベイスン・ミキサー |
  | デプロイヤーの手の物を、2つ先のブレイズバーナーへ（6つの向き） | デプロイヤー・ブレイズバーナー |
  | ベルトの両端の先のアイテムドレイン | アイテムドレイン |
  | 石臼（取り出すファンネル）、粉砕ホイールの組（下にチェスト）、ソー（まわりにチェスト） | 石臼・粉砕ホイール・粉砕ホイールの間・ソー |
  | 機械アーム（デポからチェストへ、チェストからプレスの下のデポへ） | 機械アーム |
  | 扇風機（6つの向きに、水・デポ・取り出すファンネル） | 扇風機 |

  デポは状態を持たないので、置き方の中に置いて確かめる。たどるブロックはすべて、上の置き方か、この表のどれかで確かめる（テストが調べる）。どの置き方も、どこかの状態で物が流れ、機械・トンネルの置き方では止まる時間が出ることも調べる（物が流れないと、この確かめ方は効かない）。

## 4. コードの分岐

- `src/calc/create/` の分岐の網羅率を測る（`vitest.config.ts` の coverage。`npm run coverage`）。下限は分岐 100%。
- テストで通せる分岐は、テストを足して通す。テストは対象のファイルの隣（`src/calc/create/<名前>.test.ts`）に置く。
- 通せない分岐は、その分岐の場所に印を付け、理由を書く。印そのものが「通せない分岐の一覧」になる（書類に二重に書かない）。

  ```ts
  /* v8 ignore next -- ゲームは横を向いていないベルトを残さない */
  ```

  - 印は `v8 ignore next`・`v8 ignore if`・`v8 ignore else`・`v8 ignore start` と `v8 ignore stop` の組。
  - 理由は `--` のあとに日本語で書く。ゲームが残さない状態、呼ぶ前に除いている値、型を絞るためだけの分岐、など。`start` から `stop` までは短くする。
  - `tests/verification/coverageIgnores.test.ts` が、`src/calc/create/` のすべての印に理由があること、`start` と `stop` が組になっていること、ファイル全体を外す印がないことを調べる。
- 通せない分岐を消せるなら（同じ動きのまま書き直せるなら）、印を付けるより消す。

## 確かめる段階

段階 A では、上の「対象の版」の両方の版で、Create のソースと見比べる。

### ゲームで測る（D）

- 試験台は、クリエイティブモーターで回転数を決め、調べるブロックを回す。応力の試験台は、応力計と速度計をゴーグルで見る。輸送量の試験台は、物を手で入れて（ベルトに落とす、石臼やデポを右クリック）、着くまで・処理し終わるまでの秒数を計る。
- 輸送量の試験台は、回転数を変えた版（16・64・256 RPM）を作る。
- 試験台はコードで作る（`tests/fixtures/create/testRigs.ts`）。どれも、Create 0.5.1（Create Astral）のブロックの一覧にあるプロパティをすべて書き、計算が考えたとおりに回り・流れ、ゲームで外れる置き方がないことをテストで確かめる（`tests/fixtures/create/testRigs.test.ts`）。
- 作った .nbt は作業用のフォルダに書き出し、リポジトリに入れない。書き出すと、試験台ごとの手順と、アプリが出す期待値の表（「手順.md」）も作る。Modpack を渡すと、期待値をその Modpack の設定とレシピで計算し、手順.md の見出しに Modpack のフォルダの名前を書く。

```
MINECIRCUIT_RIGS_OUT="<書き出すフォルダ>" MINECIRCUIT_MODPACK="<Modpack のフォルダ>" npx vitest run tests/verification/createTestRigsExport.test.ts
```

- 測った値は、規則ごとに記録する。合わなければ、規則とコードを直す。
- ゲームでしか分からないこと（同じ区間のベルトのファンネルとデプロイヤーのどちらが先か、機械アームの配り方など）は、先に D を行う。

### 実在の設計図で確かめる（C）

`tests/verification/realBlueprints.test.ts`。環境変数を渡したときだけ動く（ふだんの `npm run test` では飛ばす）。設計図と Modpack は利用者の PC にあるものを読むだけで、リポジトリには入れない。KubeJS のスクリプトは動かさない。

```
MINECIRCUIT_BLUEPRINTS="<設計図のフォルダ>" MINECIRCUIT_MODPACK="<Modpack のフォルダ>" MINECIRCUIT_REPORT="<報告の .md>" npx vitest run tests/verification/realBlueprints.test.ts
```

- `MINECIRCUIT_BLUEPRINTS` は `;` で区切って複数のフォルダを渡せる。中のフォルダも探す。`MINECIRCUIT_MODPACK` と `MINECIRCUIT_REPORT` は省ける。報告はリポジトリの外に書く。
- テストを失敗させること：読めない、計算が止まる、その版のブロックの一覧にない Create の ID がある、回転数が数でない、回転・つながりが設計図の外にある、物の流れの数や時間がおかしい。
- 報告に書くこと：まとめ、問題と仮定の種類ごとの数、問題の場所、ゲームが生データに保存した回転数（`Speed`）と計算の回転数の比較。設計図の外から回されていたまとまり（計算では止まるのに、保存では回っているブロックがある）には、そのブロックに保存された回転数の仮の動力源（`ST-PORT-SOURCE`）を付けて計算し直してから比べる。こうすると、動力源が設計図の外にあっても、まとまりの中の比（歯車・ベルト・ギアボックスなど）を確かめられる。比較は、保存のあとで変えた設計図などでは違ってよいので、失敗にはしない。違うブロックは1つずつ理由を見る。
- 設計図の集め方：公開されている Create の設計図は、ほとんどが createmod.com にあり、自動では集めない（利用者が選んで手元に置く）。代わりに、Create の jar の中の説明画面（ポンダー）の設計図（`assets/create/ponder/**/*.nbt`。Create の作者が組んだもの）を、利用者の jar から作業用のフォルダに取り出して通せる。説明画面の設計図は、動力源を設計図の外に置き（画面の操作で回す）、あとからブロックを足すものが多いので、上の仮の動力源を付けた比較が向く。リポジトリには入れない。
- 見方（create-stress.md「動かしたとき」）は両方で通す。`Speed` との比較は保存された状態で行う。動かしたときは、報告に問題を書き、過負荷・向きの衝突・速度の衝突・止まったネットワークが出たら1つずつ理由を見る。投稿された設計図は作った人のワールドで動いていたはずなので、出たら計算か読み取りの誤りを疑う。設計図の外につながる仕掛け（外から回す・外へ回す）や、作った人が別の Mod の値を使っていたものは、出てよい。失敗にはしない。

### 調べていること

- コードが名前で扱う Create のブロック・ブロックエンティティの種類が、どれかの版にあること。
- Create で回るブロック（`KineticBlockEntity` を継ぐクラスのブロック）と、計算で回るブロックが一致すること。
- すべてのブロックで、応力の初期値が Create のソースと一致すること。
- すべてのブロックエンティティの種類に、物の通り道での扱いが決まっていること。たどる種類にはコードに処理があり、たどらない種類にはないこと。
- すべてのブロックの、プロパティの値のすべての組み合わせ（多すぎるブロックは1つずつ）で、4回まわすと元に戻ること、反転2回で元に戻ること、値が範囲を出ないこと、東西南北の値が 90° で変わること。
- 回るブロックのすべての状態で、まわす・反転すると回転の形も同じだけ動くこと。回転軸を決めるプロパティがそろえば、どの状態でも形が決まること。
- 物の通り道でたどるブロックのすべての状態で、計算が止まらず、設計図ごとまわす・反転すると物のつながりも同じだけ動くこと。
- 物の通り道でたどるブロックのうち、真ん中に置く置き方で流れないもの（デポ・ベルトのファンネル・トンネル・上の機械・粉砕ホイール・ソー・石臼・ベイスン・アイテムドレイン・機械アーム）と扇風機のすべての状態で、物が流れる置き方ごとまわす・反転すると、物のつながりと物の動き（止まる時間も）が同じだけ動くこと。
- 応力（`ST-…`）・物の通り道と輸送量（`TP-…`）・回転と反転（`TF-…`）・置き方と初期状態（`PL-…`）の規則がすべてテストの名前に出てくること。テストに出てくる ID が書類にあること。
- 回転軸の表の行ごとに、向き・軸の値から決まる回転軸・軸の口・歯車が表のとおりであること。

### まだ仕組みがないもの

- 実在の設計図（C）の量。回転のつながりは、説明画面の設計図で多くのブロックを通せた。利用者が組んだ大きな仕掛け（ボイラー・風車・長いベルトの工場など）はまだ少ない。公開されている設計図を利用者が手元に集めれば、同じ手順で通せる。物の流れは、物の入口（仮の入出力）を置かないと通らないので、別に考える。

## 決めたこと

- **ギアボックス・ギアシフト自身の回転数は、ゲームに合わせる。** 回転が入ってきた面の回転数を出す（create-stress.md の `ST-FACE-OWN-SPEED`）。説明画面の設計図で、ゲームが保存した値と符号が逆だったため。
